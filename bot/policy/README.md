# Policy 原则

`policy` 只负责可由运行时事实确定的治理，不负责判断模型“想得是否正确”。它是安全边界和审计层，不是第二个推理模型。

## 核心原则

1. **只依据确定性事实**
   - 事实必须来自明确的生命周期事件、工具身份、结构化参数或执行结果。
   - 不解析自然语言结论，不从 shell 命令文本、输出措辞或代码内容推测意图。

2. **不把启发式判断升级为硬门禁**
   - “是否充分测试”“任务是否完成”“这是聊天还是代码任务”等语义问题不能靠正则或关键词可靠判定。
   - 此类问题应交给模型工作流、skill、提示上下文或用户确认；默认 hook 不阻断。

3. **证据必须有明确来源和有效期**
   - `ledger` 只记录专用工具已经确认的结果。
   - 读取证据只在当前执行上下文有效；新 run 或恢复会话后必须重新读取，兄弟 Agent 的读取不能作为本上下文授权。
   - 历史记录可以用于审计，但不能自动成为授权依据。

4. **门禁必须可解释、可复现**
   - 每个内置 hook 都应有单一、明确的触发条件和直接补救动作。
   - 相同结构化输入必须产生相同决定，并由边界测试覆盖。

5. **最小治理**
   - 只有存在明确安全边界、确定触发条件且误拦截成本可接受时，才增加内置 hook。
   - 可观察不等于可判定。命令数、失败数、修改文件数可以展示，但不能单独证明质量或完成度。

6. **失败时不伪造证据**
   - 被阻断或失败的工具调用不能生成成功证据。
   - 无法确认来源、版本或新鲜度的授权证据按无效处理。

## 明确不做

默认 policy 不应：

- 根据命令名称猜测是否运行了测试；
- 根据最终回答中的“完成”“已验证”等词语判定真假；
- 判断一次验证是否充分；
- 推断任务属于代码、运维或日常聊天；
- 用工具调用次数、探索分数或进度分数强迫模型行动；
- 用更多提示反复纠正无法确定的问题。

## 当前内置边界

- `read_before_write`：主 Agent 或可写子 Agent 修改已存在文件前，必须在自己的执行上下文通过专用 `read` 工具读取当前内容。
- `garbled_circuit_breaker`：连续产生明确标记为乱码的响应时终止循环。

`PreToolUse` 在主 Agent 和可写子 Agent 的工具路径执行。每个执行者使用独立授权 ledger，避免主 Agent、子 Agent 或兄弟 Agent 的读取跨上下文授权；子 Agent 工具结果以不生成授权的方式汇入主 run 共享审计 ledger。
主 run 的共享 policy 在子 Agent 路径只接收审计结果，不执行其 hooks，也不能替代或满足子 Agent 的本地写前读门禁；子 Agent 只执行每次 run 新建的本地确定性 policy。
子 Agent 当前只参与 `PreToolUse`；执行结果写入 ledger，但不触发主 Agent 的 `PostToolUse/PostToolBatch` 控制流。
`read_before_write` 是结构化调用顺序门禁，不提供文件系统事务或对外部并发修改的原子版本保证。

## 新增 hook 前的检查

只有以下问题都能明确回答，才应把规则加入默认 policy：

1. 输入事实由哪个结构化事件产生？
2. 是否完全不依赖自然语言、关键词或意图推测？
3. 是否存在低误报的确定性判定？
4. 被阻断后是否有明确、有限的恢复动作？
5. 状态在 reset、restore、失败和并发路径上的有效期是什么？
6. 是否覆盖允许、阻断、失败、恢复和绕过尝试的测试？

任一项无法回答时，优先把能力放到 `hunt`、`think`、`check` 等显式工作流中，而不是继续堆叠默认 hook 或 system prompt。

## 目录职责

- `policy.go`、`policy_tools.go`：运行时入口与生命周期衔接。
- `builtin/`：少量默认确定性 hook。
- `ledger/`：工具事实与当前 run 授权证据。
- `plugin/`：用户显式配置的扩展 hook；不代表默认治理原则可以放宽。
- `audit.go`：hook 决策的可观察记录。
